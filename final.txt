FINALNY PLAN WDROŻENIA — LOCAL BROWSER AGENT
=============================================

Dokument opisuje kolejność budowy projektu od decyzji ogólnych do szczegółów implementacji.
Każdą część należy zamknąć działającym rezultatem, testem i krótkim raportem. Nie należy
przechodzić do następnej części, jeśli kryteria wyjścia poprzedniej części nie są spełnione.

ZASADA REALIZACJI
-----------------

Projekt budujemy warstwowo:

1. środowisko i decyzje;
2. szkielet oraz konfiguracja;
3. modele, baza i zdarzenia;
4. przeglądarka;
5. orkiestrator w trybie mock;
6. API i WebSocket;
7. interfejs użytkownika;
8. prawdziwy LLM i routing;
9. bezpieczeństwo oraz human-in-the-loop;
10. odporność, benchmarki i dokumentacja.

Tryb mock jest podstawą rozwoju i testów. Integrację z Groq włączamy dopiero wtedy, gdy
cała ścieżka backend–przeglądarka–frontend działa bez sieciowego LLM.

CZĘŚĆ I — ZAKRES, ŚRODOWISKO I ARCHITEKTURA
=============================================

Cel części: ustalić, co budujemy, potwierdzić możliwości środowiska i uniknąć implementacji
opartej na nieaktualnym API.

Krok I.1 — Inwentaryzacja repozytorium

- wykonać `git status --short --branch`;
- sprawdzić remote i aktywną gałąź;
- spisać istniejące pliki oraz niezwiązane zmiany;
- określić, czy obecny `main.py` należy zachować, rozbudować czy odseparować;
- ustalić, czy istnieje frontend, system testów lub skrypt uruchomieniowy.

Rezultat: lista istniejących zasobów i ryzyk kolizji.

Krok I.2 — Inwentaryzacja narzędzi

- sprawdzić Python 3.12 lub zgodną wersję;
- sprawdzić `uv`, Node.js, npm/pnpm, Chromium i Git;
- sprawdzić możliwość instalacji zależności;
- sprawdzić port 24400 i dostęp do localhost;
- opisać ograniczenia terminala Acode.

Rezultat: potwierdzony sposób instalacji i uruchamiania.

Krok I.3 — Inspekcja Browser Use

- odczytać zainstalowaną wersję;
- sprawdzić importy Agent, BrowserSession, BrowserProfile i ChatGroq;
- sprawdzić sposób tworzenia sesji, kart, screenshotów i stanu strony;
- wykonać minimalny test otwarcia lokalnej strony;
- zapisać wszystkie sygnatury i odstępstwa od dokumentacji.

Rezultat: `docs/environment-report.md` z potwierdzonym API i ryzykami.

Krok I.4 — Zatwierdzenie MVP

MVP obejmuje tylko:

- konfigurację;
- FastAPI;
- jedną trwałą sesję Chromium;
- podstawowe akcje przeglądarki;
- normalizowany stan;
- bazę zadań;
- mock LLM;
- API, WebSocket i prosty interfejs;
- pauzę, wznowienie, stop oraz human-in-the-loop.

Routing pięciu modeli, dodatkowe role, uploady i benchmarki są rozszerzeniami po MVP.

Kryterium wyjścia części I: raport środowiska istnieje, zakres MVP jest zaakceptowany,
a eksperyment Browser Use potwierdził możliwość sterowania Chromium albo udokumentowano
blokadę i fallback.

CZĘŚĆ II — SZKIELET PROJEKTU I POWTARZALNE ŚRODOWISKO
=======================================================

Cel części: utworzyć stabilny projekt, który można zainstalować i uruchomić bez funkcji
biznesowych.

Krok II.1 — Utworzenie struktury

Utworzyć:

```text
backend/app/{api,agents,browser,communication,database,events,llm,orchestrator,safety,tasks}
frontend/src/{components,hooks,services,types}
tests/{unit,integration,fixtures}
scripts docs data
```

Dodać minimalne pliki `__init__.py` tylko tam, gdzie są potrzebne. Nie tworzyć pustych
modułów „na zapas”.

Krok II.2 — Backend i zależności

- skonfigurować `pyproject.toml` dla uv;
- dodać FastAPI, Uvicorn, Pydantic v2, WebSockets, aiosqlite/SQLite, dotenv i Browser Use;
- przypiąć wersje wykryte w części I;
- dodać narzędzia testowe i lintujące;
- utworzyć lockfile.

Krok II.3 — Frontend i zależności

- utworzyć aplikację React + TypeScript + Vite;
- dodać Tailwind CSS;
- skonfigurować skrypt build i dev;
- zdefiniować adres API jako zmienną konfiguracyjną;
- nie umieszczać sekretów w kodzie frontendowym.

Krok II.4 — Konfiguracja i dane

- utworzyć `.env.example`;
- utworzyć konfigurację Pydantic Settings;
- dodać `data/browser-profile`, `data/uploads`, `data/screenshots`, `data/logs` podczas startu;
- dodać `.env`, `data/`, profile, logi i pliki tymczasowe do `.gitignore`;
- wprowadzić bezpieczne domyślne wartości.

Krok II.5 — Skrypty uruchomieniowe

- przygotować `run.py`;
- przygotować `run.sh`;
- przygotować `run.ps1`;
- wyświetlać wyłącznie URL, status przeglądarki, liczbę slotów i ostrzeżenia;
- nigdy nie wyświetlać wartości kluczy.

Krok II.6 — Test instalacji

- zainstalować backend w świeżym środowisku;
- zainstalować frontend;
- uruchomić pusty backend;
- sprawdzić, że `GET /api/health` odpowiada;
- sprawdzić, że frontend się buduje.

Kryterium wyjścia części II: nowa osoba może zainstalować projekt według README, backend
startuje, a frontend się buduje.

CZĘŚĆ III — MODELE DOMENOWE, BAZA I ZDARZENIA
===============================================

Cel części: zdefiniować stabilny kontrakt pomiędzy UI, API, orkiestratorem i agentami.

Krok III.1 — Typy i walidacja

Zdefiniować wersjonowane modele:

- TaskCreateRequest;
- TaskRecord i TaskStatus;
- BrowserState, BrowserTab, InteractiveElement;
- BrowserAction i BrowserActionResult;
- TaskPlan;
- PerceptionResult;
- VerificationResult;
- AgentError;
- AgentEvent.

Każdy model powinien mieć typy, ograniczenia długości, wartości domyślne i czytelne błędy.
Akcje muszą mieć jawne dozwolone wartości, zamiast dowolnych słowników.

Krok III.2 — Baza SQLite

- utworzyć inicjalizację bazy;
- utworzyć tabelę zadań i indeks po `task_id` oraz timestampie;
- dodać repozytorium asynchroniczne;
- wprowadzić transakcje i bezpieczne zamykanie połączeń;
- zapisywać wyłącznie zsanityzowane dane.

Krok III.3 — Event bus

- utworzyć kolejkę zdarzeń per zadanie;
- zagwarantować kolejność i numer sekwencyjny;
- dodać timestamp ISO-8601;
- ograniczyć wielkość payloadu;
- obsłużyć brak odbiorcy oraz rozłączenie.

Wymagane eventy: task created/started/planning/completed/failed/stopped, agent
started/progress/decision, browser started/navigation/action/action_result/screenshot/state,
verification started/completed oraz task waiting_for_user/paused/resumed.

Krok III.4 — Testy kontraktów

- poprawna serializacja wszystkich modeli;
- odrzucenie nieprawidłowej akcji;
- zapis i odczyt historii;
- brak sekretów w rekordzie;
- prawidłowa kolejność eventów.

Kryterium wyjścia części III: wszystkie warstwy mają wspólny kontrakt, a testy modeli,
bazy i zdarzeń przechodzą bez przeglądarki i bez LLM.

CZĘŚĆ IV — WARSTWA PRZEGLĄDARKI
================================

Cel części: stworzyć jedną kontrolowaną sesję Chromium i bezpieczny executor akcji.

Krok IV.1 — BrowserSession adapter

- opakować aktualne API Browser Use za własnym interfejsem;
- skonfigurować widoczną przeglądarkę;
- użyć `data/browser-profile` jako trwałego profilu;
- zapewnić start, stop i idempotentne zamknięcie;
- nie implementować własnego sterownika ani Selenium.

Krok IV.2 — Odczyt stanu

Zwracać tylko potrzebny wycinek:

- URL i tytuł;
- listę kart i aktywną kartę;
- limitowany widoczny tekst;
- linki, przyciski i pola formularzy;
- metadane screenshotu;
- wersję i timestamp stanu.

Krok IV.3 — Executor

Implementować kolejno `goto`, `click`, `input`, `scroll`, `wait`, `screenshot`, `extract`,
`go_back`, `go_forward` i `reload`.

Każda akcja musi mieć walidację, timeout, pomiar latencji, zsanityzowany wynik i informację
o bieżącym URL. Domyślnie blokować akcje nieznane.

Krok IV.4 — Restart i odzyskiwanie

- rozpoznać zamkniętą sesję;
- wykonać ograniczony restart;
- ponownie użyć profilu;
- odczytać stan po restarcie;
- nie kontynuować, gdy stan jest niejednoznaczny.

Krok IV.5 — Testowa strona lokalna

Utworzyć fixture z linkiem, przyciskiem, polem tekstowym, formularzem, długą treścią i
drugą kartą. Testy nie powinny zależeć od zewnętrznej strony internetowej.

Kryterium wyjścia części IV: każda akcja MVP działa na lokalnej stronie testowej,
screenshot i stan są dostępne, a profil utrzymuje sesję pomiędzy uruchomieniami.

CZĘŚĆ V — ORKIESTRATOR I MVP BEZ LLM
=====================================

Cel części: doprowadzić zadanie od żądania do wyniku w sposób deterministyczny.

Krok V.1 — Runner zadania

- utworzyć jeden runner na `task_id`;
- zaimplementować statusy created, started, running, paused, waiting_for_user, completed,
  failed i stopped;
- dodać limit kroków i timeout całego zadania;
- użyć `asyncio.Event` do anulowania;
- sprzątać runner po zakończeniu.

Krok V.2 — Deterministyczny mock planner

- przyjąć tekst użytkownika;
- rozpoznać ograniczony zestaw scenariuszy testowych;
- wygenerować poprawny `TaskPlan`;
- przekazać akcje do executora;
- zweryfikować wynik po każdej akcji.

Krok V.3 — Pauza, wznowienie i stop

- PAUSE nie zamyka Chromium i blokuje nowe akcje;
- RESUME najpierw pobiera nowy stan;
- STOP anuluje akcje oczekujące i zachowuje profil;
- CONTINUE jest możliwe po wymaganym potwierdzeniu.

Krok V.4 — Historia

- zapisać utworzenie, rozpoczęcie i zakończenie zadania;
- zliczać akcje i wywołania LLM;
- zapisać wynik po redakcji;
- nie zapisywać wrażliwych wartości z pól.

Krok V.5 — Test end-to-end backendu

Uruchomić zadanie mockowe: otwarcie fixture → odczyt → kliknięcie → wpisanie tekstu →
ekstrakcja → ukończenie. Sprawdzić eventy, historię i obsługę STOP.

Kryterium wyjścia części V: MVP działa całkowicie bez sieciowego LLM i bez interfejsu.

CZĘŚĆ VI — API I WEBSOCKET
===========================

Cel części: udostępnić funkcje MVP przez stabilny backend HTTP/WebSocket.

Krok VI.1 — Endpointy zadań

- `POST /api/tasks` tworzy zadanie i zwraca ID;
- `GET /api/tasks/{task_id}` zwraca status oraz bezpieczny wynik;
- endpointy pause/resume/stop walidują aktualny stan;
- błędy zwracają spójny format bez stack trace i sekretów.

Krok VI.2 — Endpointy przeglądarki

- `/api/browser/state`;
- `/api/browser/tabs`;
- `/api/browser/navigate`;
- `/api/browser/reload`;
- `/api/browser/screenshot`.

Dodać limit długości URL i odrzucać nieobsługiwane schematy, jeśli nie są potrzebne.

Krok VI.3 — WebSocket

- `WS /ws/tasks/{task_id}` subskrybuje konkretny task;
- sprawdzać `Origin`;
- wysyłać bieżący status po reconnect;
- obsługiwać heartbeat i timeout;
- nie transmitować cookies ani danych profilu.

Krok VI.4 — Testy API

- health/status;
- pełny cykl tasku;
- błędny ID;
- konflikty stanów pause/resume/stop;
- kolejność eventów;
- reconnect po zerwaniu połączenia.

Kryterium wyjścia części VI: pełne zadanie mockowe można obsłużyć samymi żądaniami HTTP
i WebSocketem.

CZĘŚĆ VII — FRONTEND I UX
==========================

Cel części: umożliwić użytkownikowi wykonywanie zadań bez narzędzi developerskich.

Krok VII.1 — Typy i klient API

- odwzorować modele backendu w TypeScript;
- utworzyć klienta REST;
- utworzyć hook WebSocket z reconnect;
- pokazywać użytkownikowi bezpieczne komunikaty błędów;
- nie zapisywać sekretów w localStorage ani state globalnym.

Krok VII.2 — Layout

Zbudować oryginalny układ dwóch paneli:

- lewy: historia, rozmowa, aktywność i formularz zadania;
- prawy: podgląd przeglądarki, URL, stan, screenshot i kontrolki.

Krok VII.3 — Interakcje

- Run tworzy zadanie;
- Pause/Resume/Stop wysyłają odpowiednie endpointy;
- New Task resetuje tylko widok, nie usuwa profilu;
- preview można rozszerzyć prawie do pełnego ekranu;
- `Human interaction required` jest widoczne i jednoznaczne.

Krok VII.4 — Testy UI

- pusty stan;
- utworzenie zadania;
- streaming eventów;
- zmiana statusów;
- reconnect;
- pauza i wznowienie;
- rozszerzenie preview.

Kryterium wyjścia części VII: użytkownik może uruchomić i zatrzymać zadanie mockowe,
obserwować aktywność i stan przeglądarki w UI.

CZĘŚĆ VIII — GROQ I INTELIGENCJA AGENTOWA
==========================================

Cel części: zastąpić mock decyzjami LLM bez naruszania stabilności MVP.

Krok VIII.1 — Provider adapter

- zdefiniować interfejs wywołania modelu;
- dodać timeout, limit tokenów i walidację strukturalną;
- rozdzielić transport, prompt i walidację;
- obsłużyć brak klucza przez tryb mock lub bezpieczny komunikat.

Krok VIII.2 — Sloty Groq

- obsłużyć pięć par `GROQ_API_KEY_n`/`GROQ_MODEL_n`;
- pomijać puste sloty;
- zwracać tylko liczbę slotów i status health;
- nigdy nie ujawniać kluczy endpointem, logiem ani frontendem.

Krok VIII.3 — ModelRouter

Rejestrować latencję, timeouty, błędy API, rate limits, niepoprawne odpowiedzi i sukcesy.
Wybierać model przewidywalnie. Retry ograniczyć do błędów przejściowych i nie powtarzać
automatycznie operacji nieodwracalnych.

Krok VIII.4 — Role

Dodawać stopniowo:

1. Browser Operator dla prostych akcji;
2. Planner dla zadań wieloetapowych;
3. Perception tylko przy brakującym stanie;
4. Critic/Recovery po błędzie;
5. Judge wyłącznie przy utrzymującej się niejednoznaczności.

Każda rola komunikuje się modelami strukturalnymi, a nie długą rozmową tekstową.

Krok VIII.5 — Testy z mockiem dostawcy

- sukces poprawnej odpowiedzi;
- odpowiedź niepoprawna strukturalnie;
- timeout;
- rate limit;
- niedostępny slot;
- wybór fallbacku;
- proste zadanie korzysta tylko z wymaganej liczby ról.

Kryterium wyjścia części VIII: prawdziwy Groq może obsłużyć zadanie, a jego brak nie
degraduje ani nie wyłącza całej aplikacji.

CZĘŚĆ IX — BEZPIECZEŃSTWO I CZŁOWIEK W PĘTLI
==============================================

Cel części: upewnić się, że agent nie wykonuje nieautoryzowanych lub nieodwracalnych operacji.

Krok IX.1 — Potwierdzenia

Wymagać potwierdzenia przed wysłaniem formularza, wiadomości, zakupem, płatnością,
usunięciem danych, zmianą konta i finalizacją rejestracji.

Krok IX.2 — Wyzwania stron

- rozpoznawać sygnały CAPTCHA/MFA/Cloudflare bez ich obchodzenia;
- zatrzymać akcje;
- wysłać `task.waiting_for_user`;
- pokazać `Human interaction required`;
- pozostawić przeglądarkę otwartą;
- po potwierdzeniu ponownie odczytać i zweryfikować stan.

Krok IX.3 — Upload i dane lokalne

- sprawdzać rozmiar i typ pliku;
- normalizować ścieżkę;
- odrzucać `..`, ścieżki absolutne i pliki wykonywalne;
- generować nazwy serwerowe;
- przechowywać poza katalogiem publicznym.

Krok IX.4 — Test bezpieczeństwa

Przetestować Origin, path traversal, zbyt duży upload, logowanie sekretu, potwierdzenie
akcji i zatrzymanie na ekranie bezpieczeństwa.

Kryterium wyjścia części IX: każde działanie wysokiego ryzyka ma kontrolę człowieka,
a aplikacja nie próbuje omijać zabezpieczeń strony.

CZĘŚĆ X — ODPORNOŚĆ I OBSŁUGA BŁĘDÓW
======================================

Krok X.1 — Klasyfikacja błędów

Rozdzielić błędy na przejściowe, wymagające retry, wymagające człowieka i kończące zadanie.
Każdy błąd ma kod, bezpieczny opis, timestamp oraz informację o możliwości powtórzenia.

Krok X.2 — Restart Chromium

- wykryć crash;
- zatrzymać akcje;
- zrestartować sesję i użyć trwałego profilu;
- ponownie pobrać stan;
- kontynuować tylko przy jednoznacznym stanie.

Krok X.3 — WebSocket reconnect

- zachować historię eventów lub snapshot statusu;
- po reconnect wysłać snapshot i nowe eventy;
- nie uruchamiać drugi raz runnera;
- testować wielokrotne rozłączenia.

Krok X.4 — Testy awarii

Wymusić timeout LLM, rate limit, brak elementu, błąd nawigacji, crash Chromium, disconnect
WebSocket i STOP w czasie akcji. Sprawdzić, że operacje nieodwracalne nie są powtarzane.

Kryterium wyjścia części X: aplikacja odzyskuje się tylko w bezpiecznych przypadkach i
zatrzymuje się przy niejednoznaczności.

CZĘŚĆ XI — BENCHMARKI I OPTYMALIZACJA
======================================

Wykonywać po przejściu pełnego MVP i testów bezpieczeństwa.

Krok XI.1 — Pomiar bazowy

Zmierz: LLM latency, browser action latency, state latency, screenshot latency, całkowity
czas zadania, liczbę wywołań modeli, tokeny (jeśli dostępne) i success rate.

Krok XI.2 — Scenariusze

Porównać single agent, planner+operator oraz planner+operator+recovery. Pełne pięć ról
uruchamiać opcjonalnie i nie wybierać go jako domyślnego trybu.

Krok XI.3 — Wnioski

- zapisać środowisko i dane wejściowe;
- wygenerować timestamped report;
- wskazać bottlenecks;
- zmieniać tylko jedną optymalizację naraz;
- po każdej zmianie powtórzyć benchmark i testy regresyjne.

Kryterium wyjścia części XI: wyniki są powtarzalne i nie ma twierdzeń o wydajności bez pomiaru.

DEFINITION OF DONE
==================

Projekt jest gotowy dopiero wtedy, gdy:

- MVP działa bez kluczy Groq w trybie mock;
- serwer działa na 127.0.0.1:24400;
- UI, REST i WebSocket działają razem;
- Chromium jest widoczny i używa trwałego profilu;
- akcje mają walidację, timeouty i bezpieczne wyniki;
- pauza, wznowienie, stop i reconnect są przetestowane;
- historia nie zawiera sekretów;
- wyzwania bezpieczeństwa wymagają człowieka;
- niedostępny model nie wyłącza aplikacji;
- testy, build i dokumentacja przechodzą;
- każda funkcja oznaczona jako ukończona ma dowód w postaci testu lub ręcznej weryfikacji.
